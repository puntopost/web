1. Introducción

La API de merchant de PuntoPost permite integrar de forma directa la validación de cobertura, selección de puntos de recogida y creación de envíos desde tu sistema. Esta opción es ideal si no usas Shopify ni WooCommerce o si necesitas un flujo personalizado.

El flujo recomendado se divide en 3 fases: validación de cobertura, obtención de puntos disponibles y creación/gestión del envío + webhooks. Consulta la documentación OpenAPI completa en https://back.puntopost.mx/api/doc/merchant.

2. Requisitos previos

  • Contactar con PuntoPost para dar de alta el comercio y recibir credenciales.
  • Recibir merchant_id y credenciales del usuario merchant.
  • Configurar el tipo de comercio: B2C, C2C, C2B, C2F o F2C según tu flujo de negocio.

3. Autenticación

Usa autenticación JWT en el header Authorization enviando un token de acceso válido para merchant. El rol requerido para operar es ROLE_MERCHANT.

  • POST /api/auth/v1/users/merchant (registro)
  • POST /api/v1/auth/login (login)
curl -X POST "https://back.puntopost.mx/api/v1/auth/login" \
  -H "Content-Type: application/json" \
  -d '{
    "username": "merchant_user",
    "password": "tu_password"
  }'

4. Validación de cobertura

  • GET /api/merchant/v1/coverage/{postalCode} devuelve { "covered": true/false }.
  • GET /api/merchant/v1/coverage devuelve el listado completo de códigos postales cubiertos.

Un código postal se considera cubierto cuando el PUDO más cercano está a menos de 3 km.

{
  "covered": true
}

5. Obtener puntos de recogida (PUDOs) disponibles

Endpoint: GET /api/merchant/v1/pudos

Query params: latitude, longitude, postal_code, radius_km, cursor (paginación). 

GET /api/merchant/v1/pudos?postal_code=11560&radius_km=5
{

6. Crear un envío

Tipo Endpoint Uso
C2CPOST /api/merchant/v1/{merchantId}/parcelsCliente → cliente (ambos en PUDO)
B2CPOST /api/merchant/v1/{merchantId}/parcels/b2cComercio → cliente en PUDO
C2BPOST /api/merchant/v1/{merchantId}/parcels/c2bCliente en PUDO → comercio (devoluciones)
C2FPOST /api/merchant/v1/{merchantId}/parcels/c2fCliente en PUDO → almacén (retornos)
F2CPOST /api/merchant/v1/{merchantId}/parcels/f2cAlmacén → cliente en PUDO

Campos comunes: content, sender, receiver, origin_id, destination_id, merchant_reference (opcional, recomendado para idempotencia).

{
  "content": "Playera talla M",
  "sender": { "name": "Tienda Demo" },
  "receiver": { "name": "María Pérez", "phone": "+525511112222" },
  "origin_id": "pudo_origen",
  "destination_id": "pudo_destino",
  "merchant_reference": "ORDER-10001"
}
{
  "detail": { "id": "parcel_123", "tracking": "PPMX123456" },
  "qr": "base64_or_url_qr_tracking",
  "qr_label": "base64_or_url_qr_etiqueta"
}

Errores frecuentes: 400 (validación), 403 (permisos), 404 (no encontrado), 409 (tipo no configurado).

7. Consultar envíos

  • GET /api/merchant/v1/parcels/{identifier} — identifier puede ser id, tracking, label o merchant_reference.
  • GET /api/merchant/v1/merchants/{merchantId}/parcels — filtros: date_min, date_max, status[], query, limit, offset.

8. Transiciones de estado

  • PUT /api/merchant/v1/parcels/{identifier}/ready — marca listo en origen (CREATED → IN_ORIGIN_POINT).
  • PUT /api/merchant/v1/parcels/{identifier}/deliver — marca como entregado (solo C2B / C2F).
  • DELETE /api/merchant/v1/parcels/{identifier} — cancela el envío (solo si está en CREATED).
CREATED → IN_ORIGIN_POINT → IN_TRANSIT → IN_DESTINATION_POINT → DELIVERED
Alternativas: CANCELLED, LOST

9. Descargar etiqueta

GET /api/merchant/v1/parcels/{identifier}/label devuelve la etiqueta en PDF o PNG según la configuración del comercio.

10. Webhooks (recepción de eventos)

Configura la URL de webhook en la configuración de tu comercio.

  • parcel_status_changed (incluye status_history completo)
  • parcel_origin_changed
  • parcel_destination_changed
{
  "event": "parcel_status_changed",
  "data": {
    "id": "parcel_123",
    "tracking": "PPMX123456",
    "status": "IN_TRANSIT",
    "status_history": [
      { "status": "CREATED", "date": "2026-07-14T09:00:00Z" },
      { "status": "IN_ORIGIN_POINT", "date": "2026-07-14T10:00:00Z" },
      { "status": "IN_TRANSIT", "date": "2026-07-14T12:00:00Z" }
    ]
  }
}

Buenas prácticas: responder HTTP 2xx rápido, procesar de forma idempotente y aplicar reintentos con backoff ante fallos temporales.

11. Errores comunes y buenas prácticas

  • Usa merchant_reference para idempotencia y evitar duplicados.
  • Rota periódicamente el JWT y controla su expiración.
  • Maneja paginación incremental con cursor en listados de PUDOs.
  • Valida con soporte el entorno de sandbox vs producción antes de salir a producción.

12. Recursos

  • OpenAPI completa: https://back.puntopost.mx/api/doc/merchant
  • Soporte técnico: contacta a tu ejecutivo de PuntoPost para credenciales, configuración de tipos de comercio y webhook.
